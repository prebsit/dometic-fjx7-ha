## Findings
- BLE at ESPHome 2026.9's default 100% scan duty starves the setup hotspot:
  phones see it but can't finish the WPA2 handshake. Fix: BLE off until
  first WiFi join (packages/provisioning.yaml).
- Captive portal logs the user's WiFi password at INFO. Shipped firmware
  should run the logger at WARN.
- iCloud Keychain syncs hotspot passwords between Apple devices: forget the
  network on ALL devices before testing a typed join.
- Hotspot twice invisible to phone while the chip reported it broadcasting;
  cleared by a board reset. Not reproduced since. Setup card should say
  "can't see it? unplug for 5 s".
- This board reads -81 to -90 dBm at 1 m from the router (van bridge, same
  model, gets -62 to -72 from a cupboard). Suspect antenna/batch. TODO:
  compare with another SuperMini, and out of the case.

## Protocol findings (FJX7, firmware on SHE_36bd48)
- Adverts: name SHE_xxxxxx, flags 0x06, two manufacturer-data entries under
  company ID 0x0845.
  - Entry 1: 04 + base MAC (6 bytes) + ASCII "9600051000" (looks like the
    Dometic article number; unverified).
  - Entry 2: one byte. 0x00 normal, 0x01 in pairing mode (hold + and - on
    the panel 3 s; lasts ~60 s).
- BLE address = base MAC + 2 (name SHE_36bd48, BLE 68:FE:71:36:BD:4A).
- "Ignoring unexpected GAP event type: 9" x4 on every encrypted connect
  (pairing and reconnect). Harmless so far; consider silencing.

## More findings
- Bluetooth now starts only after WiFi connects (every boot). Did NOT fix
  the first-attempt WiFi failures after a reboot (seen with BLE fully off).
  Current theory: GL.iNet still holds the old session after an unclean
  reboot. Costs ~10 s per boot, always recovers. Unproven.
- Component quirk (pre-existing): 30 s poll timer starts at 0, so it
  re-subscribes immediately after the first subscribe. Harmless; 2-line fix.
- BLE RSSI from this board to the AC: -78 to -100 depending on placement.
